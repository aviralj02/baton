Baton

Raycast,
but for context.

A wiki about everything you are building, written by the agent that did the work. One command files it. One hotkey hands it back.

The problem

The handoff is a chore, and you are the one doing it

You finish a long session with an agent. It understands the problem. You open a new window and that understanding is gone. You can recover it, by asking the first agent to write a handoff, and that works fine.

The chore is the problem. Not the missing context, which you can always rebuild if you are willing to pay for it in effort. Baton removes the effort.

What /baton actually does

It is a text file, not a program

Typing it pastes a markdown instruction file into your current conversation. The agent is still in the same session, so everything from the last two hours is already in its context. It does not re-read anything. It just gets told what to do with what it already knows.

/baton  →  ~/.claude/skills/baton/SKILL.md   injected as instructions

  Read   ~/Baton/AGENTS.md        page types, sections, granularity rule
  Read   ~/Baton/index.md         what pages already exist
  Bash   pwd                      resolve cwd → projects/baton/
  Read   the few relevant pages

         compares this session against what those pages claim
         emits a proposal

  ── you accept ──

  Write / Edit the pages, regenerate index.md, append to log.md

Ordinary file writes. Baton is not involved until the files change, at which point its watcher re-indexes them so the hotkey can find them.

The consequence

Baton never calls a model. Understanding the session is the agent. Writing pages is the agent. Search is FTS5. The primer is text composition. So there is no API key, no proxy, no rate limit and no cost per use. The two things blocking Milestone 3 do not get solved, they stop existing.

The one gap: a browser chat cannot run a command. Paste it into a terminal agent and run it there.

One PRD reversal to record

PRD decision 2 says store JSON, not markdown, because updating prose means re-parsing prose. True for one flat seven-field document. False for many small typed pages, where an update means rewriting one 200 word page. And the writer is now an agent with file tools, for which editing markdown is native and round-tripping JSON through a Rust command is not.

Start here

The first step needs no Rust at all

The riskiest assumption is not the launcher. It is whether an agent, asked to file what it learned, writes pages good enough to be worth reading. You can test that today, in about an hour, with no code.

Step one: write the schema and the skill

  • Create ~/Baton/AGENTS.md. Define the five page types (project, decision, attempt, component, gotcha), their required sections, the frontmatter fields, and the granularity rule. One page per thing you would search for, anything smaller is a section.
  • Create ~/.claude/skills/baton/SKILL.md. Roughly forty lines: read the schema, read the index, resolve the project from pwd, propose edits, flag conflicts, write nothing until accepted.
  • Hand-write ~/Baton/projects/baton/overview.md so there is something to update.
  • Run /baton at the end of a real session. Read the pages it wrote.

The test: paste those pages into a fresh window and start working. If it needs no correction from you in the first few exchanges, the idea works. If it does, the fault is in AGENTS.md, which is a text file you fix in a minute rather than a pipeline you rebuild.

Only after that passes is the Rust worth writing.

What this does to the existing code

Untouched: the launcher, the NSPanel work, the shortcut, the tray, FTS5, the clipboard boundary. All the hard-won stuff.

Changes: db.rs becomes an index over files, context.rs becomes page types. Both are the youngest and best-tested parts.

No longer needed: ai.rs, the proxy deploy, the rate limit namespace, the keychain entry. Keep proxy/ in the repo as a dormant option rather than deleting it.
